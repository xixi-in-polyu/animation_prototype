# Animation Production

Produce a coherent, editable, narrated animation project rather than arbitrary React or Remotion code. Treat the portable project bundle—`AnimationProject` JSON, synchronized TTS audio, caption data, and delivery metadata—as the deliverable and the repository player as the preview runtime. Planning artifacts and bundle manifests do not expand the `AnimationProject` schema unless the repository model explicitly changes.

## Establish the task

Accept a PDF, source deck, topic, outline, knowledge points, narration script, or an existing project. Preserve explicit duration, locale, tone, audience, aspect ratio, voice, brand, and theme choices. If they are absent, infer conservative defaults instead of blocking: use English for the project, narration, and captions; the platform's stable English `default-academic` voice profile; 16:9; 30 FPS; `white-editorial`; and a duration derived from selected concepts rather than source page count. Estimate spoken duration from 135–155 English words per minute plus deliberate scene pauses, record the estimate in the Reel Read, and revise it after measuring TTS. `white-editorial` means a pure-white canvas with Times New Roman as the first-choice font.

Request synchronized TTS audio and caption timing from the supported platform TTS API by default. Read [references/narration-audio.md](references/narration-audio.md) before submitting narration. The LLM supplies text and semantic delivery intent; it must not receive provider credentials, call a TTS vendor directly, or write provider-specific voice IDs into the project. If the platform API is unavailable, emit a portable `tts-request.json`, mark synthesis as pending or unavailable, and report that the bundle is not yet narrated; do not silently fall back to direct provider calls or browser speech. Do not perform local final-video rendering, create one-off Remotion render adapters, or encode per-scene or master MP4 files as part of normal production. Final MP4 is a separate platform export and should burn captions in by default. Invoke that export only when the user explicitly requests MP4 and the repository exposes a supported export capability. If it does not exist, report the narrated project as ready for platform export only after required audio and captions exist; do not silently fall back to a long local render. Do not modify renderer or editor source code unless the user explicitly asks for a product change.

Find the Storyline Studio repository root by locating `src/model/types.ts` and `package.json`. Read the canonical model files when they may have changed; repository code wins over these references.

## Choose the operating mode

- For a new animation, read [references/reel-read.md](references/reel-read.md), [references/aesthetic-defense.md](references/aesthetic-defense.md), and [references/light-theme-catalog.md](references/light-theme-catalog.md), then [references/choreography.md](references/choreography.md) and [references/project-contract.md](references/project-contract.md). Start from [assets/starter-project.json](assets/starter-project.json) when it saves work.
- For a PDF or PDF-derived source, first read [references/pdf-ingestion.md](references/pdf-ingestion.md). Prefer the platform source-document API for deterministic extraction, native image recovery, page rendering, storage, crops, and later evidence reinspection. Complete semantic analysis, candidate-page visual analysis, and the `SourcePackage` quality gate before treating the source as ready for formal animation production. When a source-specific visual is not catastrophically degraded, retain it as `original`, `crop`, or `show-then-reconstruct`; mild softness, theme mismatch, asset work, or reconstruction convenience are not reasons to discard it. If the platform API is unavailable, do not silently create a one-off extractor; obtain approval for the recorded local adapters in the references or stop at a labelled draft.
- When source slides, document imagery, or repository code inform the animation, read [references/source-assets.md](references/source-assets.md), [references/source-use-plan.md](references/source-use-plan.md), and [references/visual-explanation.md](references/visual-explanation.md). Catalog source material and create a `SourceUsePlan` before choosing final visuals. For PPTX, prefer native extraction; if a PDF is the only reliable rendered representation, also follow the PDF ingestion reference.
- For a revision, inspect the existing project first, retain stable IDs for unchanged objects, and read only the relevant reference sections.
- For a storyboard-only request, return the scene plan without manufacturing JSON.
- For validation or repair, run `node skills/animation-production/scripts/validate-project.mjs <project.json>` and repair errors before warnings.

## Production loop

For PDF input, finish the five-stage source workflow before this loop: deterministic extraction, LLM semantic analysis, candidate-page visual escalation, `SourcePackage` quality gate, then formal animation production. A package that fails the gate may support a clearly labelled draft storyboard, but not verified narration, diagrams, or source visuals.

1. For source-based work, choose `source-forward`, `balanced`, or `reconstruction-first` and write a `planned` SourceUsePlan before storyboard authoring. Use semantic planned scene IDs rather than inventing project IDs. After authoring, add actual implementation IDs and change the plan to `final` before audit. Use `source-forward` when the user asks to maximize PDF or deck use. Every approved visual candidate needs exactly one final disposition; do not let approved imagery silently disappear. See [references/source-use-plan.md](references/source-use-plan.md).
2. Write a lightweight Reel Read before project modeling: `takeaway`, `hook`, `signature`, `benchmark`, `forbidden`, `antiDefault`, and `themeDecision`. Select only from `indigo-porcelain`, `monochrome-print`, and `white-editorial` using [references/light-theme-catalog.md](references/light-theme-catalog.md). User choice overrides automatic selection. Use `white-editorial` when the subject has no clear thematic signal; do not force an academic theme merely because the input is a document. Apply the selected theme once at project level and keep it unchanged across all chapters and scenes. Record the scene format separately from the visual style. Treat common AI styling as an unchosen default, not a neutral starting point.
3. For a substantial new animation, draft three genuinely different storyboard/style-frame directions before the full JSON. If the user is present for an iterative workflow, pause for a choice. If they explicitly requested the complete result in one pass, select the strongest direction with a written rationale and preserve the alternatives.
4. Define the through-line: audience, promised outcome, opening tension, chapter progression, and closing takeaway.
5. Allocate duration across chapters and scenes according to idea complexity. Give every scene one communication job and one dominant visual explanation. For source-based work, map the important concepts to source evidence, a visual form, and the narration beat that will explain it; use [references/visual-explanation.md](references/visual-explanation.md). When the concept is relational, identify its entities and connections first. Use a `diagram` element with explicit `nodes` and `edges` for a tree, branching decision, conditional route, or multi-path system; reserve `flow` and `topology` for simpler linear relationships.
6. Write narration before fine motion. Segment it into timed units with no gaps or overlaps unless silence is intentional.
7. Submit the approved narration and semantic voice/delivery settings to the platform TTS API. Consume its measured duration, alignment, asset IDs, and bundle-relative audio URIs; align narration segments and scene duration to that result, generate captions from the same timing source, and write the portable narration manifest described in [references/narration-audio.md](references/narration-audio.md). Resubmit only affected scene audio when narration changes. If synthesis cannot run, stop at the explicit pending-audio state defined there rather than calling a provider directly.
8. Select the smallest supported element vocabulary that communicates the idea. Prefer a readable source diagram or a reconstructed explanatory visual when it shows a mechanism, relationship, comparison, or change more clearly than labels. Use `show-then-reconstruct` when viewers should see both the original evidence and its editable explanation. Use text and cards for their actual teaching job, not as a default substitute for available evidence. Keep visible copy shorter than narration and avoid repeating the same composition scene after scene. Every gradient, glow, glass surface, floating card, decorative particle, and ambient loop needs an information function or a stated benchmark rationale.
9. Choreograph motion from narration beats. Motion must explain hierarchy, sequence, comparison, change, or emphasis; decorative ambient motion is secondary.
10. Build schema-version-5 JSON, preserving source provenance only when the user actually supplied it. Never invent page citations, file/line references, or source documents. Reference copied project assets by stable asset ID rather than external absolute paths. Update the `SourceUsePlan` with the final project asset and element IDs.
11. Apply the three review layers in [references/review.md](references/review.md): structural validation, visual review, then narrative, pacing, and audio-synchronization review. Include a source-to-screen audit for source-based projects: important source ideas should be explained accurately at a readable scale, while omissions should reflect the target duration and learning goal. Run `validate-source-package.mjs` and `audit-source-use.mjs` for source-based work. `validate-project.mjs` passing proves structure only.
12. Preview the imported project with its generated audio in Storyline Studio. Generate a feedback checklist with `create-preview-feedback.mjs`, collect timestamped feedback, revise, and preview the changed version again. Use `check-preview-feedback.mjs` to find unreviewed samples. Representative screenshots are sufficient for visual evidence; do not render a complete MP4 merely to review the project. Do not describe a validator pass as visual or audio approval.

## Delivery rules

When creating a file and no path is specified, write `output/<project-slug>.animation.json`, creating `output/` if needed. Do not overwrite an existing project without inspecting it and preserving user work.

The normal delivery is an editable narrated-project bundle, not a rendered video. When platform synthesis succeeds, include the project JSON, portable audio assets, `tts-manifest.json`, captions derived from the same timing data, and `delivery-manifest.json`. When it cannot run, include `tts-request.json` and a delivery manifest that truthfully records pending or unavailable synthesis; do not claim narrated playback or MP4 readiness. The delivery manifest records whether MP4 was requested, whether platform export is available, and `burnCaptions: true` as the default export preference. Do not include provider credentials, local render scripts, per-scene MP4 files, or a master MP4 unless the user separately requested export through a supported platform capability.

Report the project path, TTS request and synthesis status, audio and caption paths when available, semantic voice profile and returned provider metadata, Reel Read/direction artifact when created, `SourceUsePlan` and source-use audit result for source-based work, total duration, scene count, structural validation result, visual review status, narrative/pacing/audio-sync review status, Storyline Studio import and narrated-playback status, MP4 export status, and any remaining caveats. Use `not-requested`, `ready-for-platform-export`, `export-requested`, or `export-unavailable` for MP4 status. Summarize approved visuals used as original/crop, shown then reconstructed, reconstructed, reference-only, and excluded. A passing structural validator is necessary but does not prove that typography, density, motion, pacing, or audio synchronization looks good.
